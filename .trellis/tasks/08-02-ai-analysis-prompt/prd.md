# AI 数据分析 Prompt 重写

## Goal

`packages/core/src/ai/buildPrompt.ts` 里那份 Prompt 是两端共用的唯一一份，但它有一个根因缺陷：**从头到尾没告诉模型这些"次数"是什么行为的次数**，只说了句"健康数据分析助手"。而它偏偏又要求模型判断"当前频率是否偏高" —— 没有参照物，模型只能先猜这是什么行为再瞎给结论。这是输出发虚的根源。

同时，请求的发送方式有两个会**直接让功能不通**的问题：写死的 `max_tokens` 对推理型模型会 400 报错，且思考过程会吃掉这个额度导致正文为空。

本任务重写这份 Prompt 与它的发送方式。**不动可配置化**（那是另一个方向，需求方明确选择先把默认的改好）。

### 两端渲染方式不同，这直接决定 Prompt 该怎么要求格式

| 端 | 渲染代码 | 行为 |
|---|---|---|
| 桌面端 | `StatsChart.tsx:544-551` | `aiResult.split("\n")` 按**单换行**拆，`filter` 掉空行，每行一个 `<Text>` |
| 移动端 | `stats.tsx:181-185` | `aiResult.split("\n\n")` 按**空行**拆段，每段一个 `<Text>` |

**两端都不解析 Markdown**（`package.json` 无任何 markdown 渲染库）。所以模型默认输出的 `**粗体**`、`### 标题`、`---` 会原样显示成裸露的星号井号横线 —— 现在的 Prompt 完全没禁止这些，这个问题大概率**当下就在发生**。

由这两行渲染代码推出的格式要求：**段落之间空一行、段落内部不要换行**。

- 段内换行 → 桌面端把段内每行拆成独立 `<Text>`，段落结构丢失
- 只用单换行分段 → 移动端整块塞进一个 `<Text>`，段间距丢失

本地分析那套规则的输出（`join("\n\n")`）正好符合这个格式，API 路径应对齐。

### 需求收敛结论（grilling 会话，11 项决策已确认）

1. **明说这些记录是什么，并硬性约束口吻。** README 自己的口径就是直白的（「打飞机记录工具 / masturbation recording tool」），Prompt 里明说与项目一致，不违和。同时必须硬性要求：中立、不评判、不说教、不建议就医。

   明确排除：只说"私密的个人行为记录"不点名（模型仍不知道"多少算多"，频率判断还是靠猜）；继续不说（最严重的问题原封不动）。

2. **人格设定拆到 system 层**，数据留在 user 消息。

   这一条与下面第 6、7 条（砍掉两个参数）的兼容性逻辑**看似矛盾，实则不同**：`temperature` / `max_tokens` 是**现役**主力型号就会报错；而不支持 system 的只有已退场的老型号（o1-preview / o1-mini 一类），现役的 GPT-4o/5、Claude、Gemini、DeepSeek、Qwen 全部支持。所以砍参数、加 system，两件事并不冲突。

3. **频率判断保留"必须给方向性结论"，但「数据够不够」由代码判定，不交给模型。**

   需求方原本选的是"保留绝对判断但允许它说数据不够"，被指出这等于给模型一个打太极的借口后，改为把判定权收回代码。

   门槛：**总记录数不足 10 条，或记录跨度不足 14 天** → 发「只描述观察到的模式、不下频率结论」的指令；两个条件都满足 → 发「必须给出偏多/正常/偏少的方向性判断并说明依据，禁止用『因人而异』『建议咨询专业人士』一类的话敷衍」。

   明确排除：把一把人群基准尺子写进 Prompt（那把尺子是需求方自己拍的、不是医学共识，写进代码等于项目在发健康建议）；不分岔让模型自己判断该走哪条（它会滥用）。

4. **给数据结构补一个"记录跨了多少天"。** 门槛判断需要它；顺带补上模型现在连"你总共记了多久"都不知道的信息缺口 —— 它目前只能从月度趋势瞎猜。

   注意这不算"新增分析维度"（需求方没选那个方向），它是第 3 条门槛的必要前提。

5. **0 条记录直接短路，不发请求**，返回与本地分析一致的那句话。

6. **不传 `temperature`。** 需求方指出「现在各家都是 thinking 模型，temperature 意义不大」—— 这个判断成立，且理由比"意义不大"更硬：OpenAI o 系列收到 `temperature` 直接 400，Claude 开思考模式时只接受 1。**不是可以不设，是不能设。**（现状本来就没传，本条是把它固化成明确决定，防止后人"顺手补上"。）

7. **不传 `max_tokens`。** 两个致命问题：o 系列只认 `max_completion_tokens`，传旧字段直接 400 —— 也就是**用户配了 o3/o4-mini，这个功能现在就是不通的**；且思考型模型的思考过程会吃掉这个额度，1024 很可能思考完就没了，正文返回空，再撞上「API 返回格式异常」。长度改由 Prompt 约束。

   明确排除：保留但调高到 4096（对 o 系列仍然报错）；按模型名判断该传哪个字段（用户可以填任意模型名，包括中转站的自定义名字，清单永远跟不上）。

8. **明令禁止 Markdown 符号**（星号、井号、横线等），因为两端都是纯文本渲染。

9. **总长度限制 400 字**，但**不固定三段结构**，让模型自由组织。需求方明确不要固定小标题。

10. **格式要求**：段落之间空一行、段落内部不换行（依据上面两端渲染方式的差异推出）。

11. **必然连带**：更新 `packages/core/test/ai.test.ts` 里对 Prompt 内容的断言。

### 明确不做（已确认排除，不要顺手做）

- **Prompt 可配置化**（存进设置、两端设置界面加输入框）。需求方选择先把默认的改好，可配置是独立方向。
- **正文为空时的错误提示优化**、回退去读思考字段当正文显示。需求方明确排除。
- **新增分析维度**（备注内容、间隔天数、最近一周明细等）。需求方没选这个方向。「记录跨了多少天」是第 3 条门槛的必要前提，不属于此项。
- 改动 `AnalyzeLocally` 的分析规则本身（它不走模型，与本任务无关）。仅允许把它 0 条记录的那句硬编码字符串抽成共用常量。
- 改动两端的渲染代码。本任务通过 Prompt 适配现有渲染，不动 `StatsChart.tsx` 和 `stats.tsx`。

## Requirements

### 一、`packages/core/src/ai/ai.types.ts`

1. 给 `IAiAnalysisData` 增加一个字段，表示这批记录覆盖了多少天：

```typescript
readonly RecordSpanDays: number;
```

### 二、`packages/core/src/ai/buildAnalysisData.ts`

2. 计算 `RecordSpanDays` = **最晚记录与最早记录之间的完整天数**，即 `Math.floor((最晚 EndTime - 最早 EndTime) / 一天的毫秒数)`。

   - 0 条记录 → `0`（走现有的全 0 分支）
   - 1 条记录 → `0`
   - 不要按日历日计算，用实际经过时间，避免时区问题

3. 不要新增遍历。现有循环已经在逐条处理 records，顺便取最早/最晚即可。

### 三、门槛常量

4. 新增两个**导出**的常量（供 `BuildPrompt` 与测试共用，遵循 `statsWindow.ts` 里"文案与实现同源"的既有惯例）：

```typescript
export const MIN_RECORDS_FOR_FREQUENCY_VERDICT: number = 10;
export const MIN_SPAN_DAYS_FOR_FREQUENCY_VERDICT: number = 14;
```

   放置位置你自行判断（`ai.constants.ts` 新文件，或就近放在 `buildPrompt.ts` 里导出），说明理由。必须从 `packages/core/src/index.ts` 导出。

### 四、`packages/core/src/ai/buildPrompt.ts`

5. 拆成两部分导出：

   - **system 内容**：静态常量（人格设定、口吻约束、输出格式与长度约束）。它不依赖数据，所以是常量而非函数。
   - **`BuildPrompt(data)`**：数据部分 + 依数据而定的分析指令。仍是纯函数吃 `IAiAnalysisData`。

6. system 内容必须包含以下要素（**具体文案由你起草，起草后我会给需求方过目定稿**）：

   - 明说这是什么记录（自慰／打飞机行为的时长与频率记录，用词与 README 一致，不必委婉但也不必粗俗）
   - 硬性口吻约束：中立、客观、不做道德评判、不说教、**不要建议就医或咨询专业人士**
   - 禁止 Markdown：不得使用 `*`、`#`、`-` 等符号做强调或标题，只输出纯文本
   - 段落之间空一行，段落内部不要换行
   - 总长度不超过 400 字
   - 不要固定小标题或编号结构，自然成段

7. `BuildPrompt(data)` 的数据部分保留现有全部内容（统计概览、高峰时段前 3、星期分布、时长统计、月度趋势最近 6 个月），**外加**新的记录跨度信息，让模型知道这批数据覆盖了多长时间。

8. 分析指令按门槛二选一：

   - `data.TotalCount >= MIN_RECORDS_FOR_FREQUENCY_VERDICT` **且** `data.RecordSpanDays >= MIN_SPAN_DAYS_FOR_FREQUENCY_VERDICT` → 要求模型**必须**给出「偏多／正常／偏少」的方向性判断并说明依据，并**明确禁止**用「因人而异」「建议咨询专业人士」这类话敷衍
   - 否则 → 明确告知记录量还少，要求**只描述观察到的模式、不下频率结论**

   两套指令都要求给出简短建议与行为模式描述（这部分不受门槛影响）。

### 八、需求方看过 Prompt 全文后的裁决

第一轮实现完成、`npm run check` 全绿后，需求方通读了 system 与 user Prompt 全文，采纳了实现报告里提出的四个问题，追加以下四项修改。

17. **数据段去掉 `- ` 行首前缀。** `BuildPrompt` 的数据段原本每行以 `- ` 开头，四十来行。模型会模仿输入格式，而这份 Prompt 的核心任务之一就是压住 Markdown —— 一边禁短横线一边示范四十行短横线，是自己拆自己的台。

    - 数据段**不再出现任何 `- ` 行首前缀**，改用缩进（实现采用两个空格缩进）。
    - **不要动数据值里本来就含短横线的内容**，例如月份 `2026-03`。那是数据值不是列表符号，去掉会破坏数据。
    - 整个 user 消息里不含任何 `*`、`#`、`|`、反引号，也不含作为列表符号或分隔线用途的 `-`。

18. **把「简短建议」改成观察式建议。** 两个门槛分支共用的那句「……并给出简短建议。」措辞太软，与「必须给出频率判断」的张力不一致。改为明确要求**基于数据的观察式建议、不要劝诫**。

19. **把 `AnalyzeLocally` 里的说教改掉。** `analyzeLocally.ts` 原第 41 行硬编码「近 7 天 N 次，频率偏高，建议适当控制。」—— 正是新 system prompt 明令禁止的劝诫。同一个 App 里选「本地分析」会说教、走 API 则中立，用户切一下 Provider 就能看到这个差异。

    - 改成中立措辞，与新 system prompt 的口吻一致（不劝诫、不暗示需要节制）。
    - 通读 `analyzeLocally.ts` 全文，其余劝诫或价值判断措辞一并改掉。
    - **保留它的绝对频率判断**（偏平稳 / 中等 / 偏高 这类分档）。**不要**给本地分析补「记录不足就不下结论」的门槛逻辑 —— 那超出本次裁决范围。

20. **高峰时段只列真实发生过的时段。** `hourlyPeaks` 原本直接对补齐成 24 个槽位的分布排序取前 3，记录少时会输出 `3:00：0 次` 这种从未发生过的时段，而新指令又要求模型必须讲时段偏好，等于请它点评不存在的事。

    - 先过滤掉 `Count === 0` 再排序取前 3，不多于 3 个就列几个。
    - 写法对齐 `analyzeLocally.ts` 已有的 `.filter((item) => item.Count > 0)`，不另创一种。
    - 星期分布**刻意保留**零值：它只有 7 个槽位且是完整分布，「周日：0 次」是有效信息（说明该用户从不在周日记录），与补齐出来的 24 个整点性质不同。
